## 十四、网络与解析：本项目的配套知识点

这一节只讲两个问题：为什么本项目的「解析」和「判定」不用大模型，以及面试里绕不开的工具与术语到底指什么。

先说结论：**模型负责「读懂人话」，代码负责「每次都对」。** 两者分工，不是替代。

### 1. LLM 到底是什么（一句话版）

- **一句话**：LLM 是一个「给定前文、预测下一个 Token」的概率模型。它擅长把人话整理成人话，但它是概率模型，不是数据库，也不会自己查证。
- **最容易搞错**：同一个问题问两次，回答可能不一样；它会产生「看起来很对但漏了一项」的结果，而且不会报错。
- **落到项目里**：凡是「必须每次结果一致」的工作——解析配置、比对差异、计算金额——都交给代码；模型只做解释、归纳、草稿。

### 2. 为什么解析配置不用 LLM

| 维度 | 确定性代码（本项目做法） | 大模型 |
| --- | --- | --- |
| 结果稳定性 | 同一输入永远同一输出，可回归测试 | 受采样与上下文影响，可能漂移 |
| 失败方式 | 不认识的那一行会被记录下来 | 可能安静地漏掉一项，不报错 |
| 成本 | 本地毫秒级，零费用 | 每次调用付费，长配置更慢更贵 |
| 可解释性 | 每个值能指回源文件行号 | 只能给出一段自然语言解释 |

分工：代码负责解析和判定；模型只把判定结果翻译成人话、生成变更单草稿。解释错了，判定结果也不会被改。

### 3. Batfish 是什么，为什么不用它

- **一句话**：Batfish 是一个开源的网络配置分析器（Java）。它把设备配置读进去，建一个虚拟网络模型，回答「某个包从 A 到 B 能不能通」「这条 ACL 会不会误拦」这类问题。
- **区别**：Batfish 做「全网转发语义仿真」，本项目做「配置版本 + 基线 + 规范判定 + 审批」。前者算包往哪走，后者回答：偏离基线了吗、违反哪条规范、证据在第几行、谁审批的。
- **为什么不直接用**：引入 Batfish 要 Java 环境和完整设备快照模型，输出也不对应我们需要的「规则 ID + 配置行号」。
- **面试标准答法**：「我们不宣称比 Batfish 更懂转发，只宣称在自己的范围内可复现、可追溯。」

### 4. 本节术语

| 术语 | 一句话解释 | 最容易搞错的地方 |
| --- | --- | --- |
| FRR | 开源路由软件，可跑在 Linux 容器里充当路由器 | 它是软件路由器，不是厂商硬件 |
| OSPF | 路由器之间互相通告网段、自动计算路径的协议 | 它是协议名；配置写在 router ospf 段里 |
| Area（区域） | OSPF 的逻辑分区，同区域路由器才直接交换明细 | 同一链路两端 Area 不一致，邻居建不起来 |
| Cost（开销） | 每条链路的代价，选路时累加，越小越优先 | 改 cost 不会立刻断网，但会改变流量走哪条路 |
| passive-interface | 让接口只通告网段、不建立 OSPF 邻居 | 接终端和服务器的接口通常要设成 passive |
| 配置漂移 | 当前配置与「基线」不一致的地方 | 漂移不等于错误，要先判断是否违反规范 |
| 基线（Baseline） | 被选定期望状态的某个配置版本 | 基线不是「最新版」，而是你选定的一版 |
| 幂等（Idempotent） | 同一请求执行一次和多次，结果一样 | 重试能安全工作，前提就是幂等 |
| 哈希（Hash） | 把内容压成固定长度指纹，内容一变指纹全变 | 哈希不能还原原文，只能用于比对 |
| 规范化（Canonicalization） | 先统一形式（排序、去空白）再比较 | 不规范化会把顺序不同误判成内容不同 |
| 三值逻辑 | 判定结果是「是 / 否 / 无法判定」三种 | 把「无法判定」当成「通过」是最危险的错误 |
| 证据链 | 结论 → 规则 → 配置行 → 原始文件，每一环可核对 | 只有结论没有证据，等于不可审计 |

### 5. 本项目的三个关键决定

- 双哈希：raw 哈希证明文件没被改过；canonical 哈希证明语义没变。加注释、换顺序，raw 变、canonical 不变。
- 未知行不丢弃：解析器遇到不认识的命令会记录下来，相关判定返回「无法判定」，绝不静默当成没问题。
- 版本只追加：配置版本不可覆盖，每次导入生成新版本并保留行号，任何结论都能回到当时那一版。

**一句话总结**：让「不知道」和「出错」都能被发现，而不是被隐藏。
