# 面试知识点（随代码进展更新）

记录方式：一条知识点 = 代码里的具体决定 + 面试可能怎么问 + 怎么答。

---

## 1. 为什么用确定性解析器，而不是把配置丢给 LLM？

**代码**：`domain/netcfg/parser.py` 用一组明确的正则和行状态机解析，未知行记录到 `unparsed`。

**面试会问**："既然有 LLM，为什么还自己写解析？"

**答**：

1. 判定必须**可复现**。同一份配置跑十次必须得到同一结论，否则无法回归测试。
2. LLM 的失败模式是"看起来对但漏了一项"，而且漏了不会报错；解析器的失败模式是"这一行不认识"，会被记录。
3. 成本：一万行配置每次调模型既慢又贵。
4. 分工：**解析和判定用确定性代码，解释和草稿才用 LLM**。

**追问**："那 LLM 还有什么用？"

**答**：把结构化 Finding 翻译成人能读的解释、生成变更单草稿、回答自然语言问题。这三件事错了不会影响判定结果。

## 2. 双哈希：raw hash 和 canonical hash

**代码**：`raw_sha256` 对原始字节做 SHA-256；`canonical_sha256` 先归一化成排序后的字典再哈希。

**面试会问**："为什么需要两个哈希？一个不够吗？"

**答**：

- `raw` 用来证明**文件没被改过**（完整性问题）
- `canonical` 用来证明**内容语义没变**（比较问题）

例子：加一行注释、交换两个 interface 块的顺序，raw 变了，canonical 不变。如果只有一个哈希，就会误报"配置变更"。

**追问**："归一化时排序，会不会丢掉顺序信息？"

**答**：会，而且这是刻意的。FRR 里 interface 块的顺序不影响语义，所以排序是安全归一化。但有些配置顺序**有意义**（如 ACL 规则顺序），那种情况就不能排序——所以归一化规则必须按语法逐条声明，不能全局套用。

**再追问**："这和幂等有什么关系？"

**答**：幂等的本质是"同样的输入得到同样的结果"。canonical hash 可以作为缓存键、去重键和回归基线。如果哈希不稳定，同一份配置会被当成两次变更。

## 3. 为什么配置版本只追加、不覆盖？

**代码**：设计中的 `ConfigVersion` 不可变，每次导入产生新版本（W2 实现）。

**面试会问**："为什么不直接存最新配置？"

**答**：

1. 审计要求：谁在什么时候改了什么，必须能回溯
2. 比较要求：漂移检测的本质是"当前 vs 基线"，基线可能是任意历史版本
3. 事故复盘：出问题时需要看"变更前"的配置
4. 成本很低：配置文件是文本，存全量比存 diff 简单得多，而且不会因为中间版本丢失导致 diff 链断裂

**追问**："全量存储会不会太大？"

**答**：单份 FRR 配置通常几 KB 到几十 KB。即使 1000 个版本也只有几十 MB。**先选简单正确的方案**，真有容量问题再加压缩或内容寻址存储。

## 4. 每个值都带行号

**代码**：`Interface.start_line/end_line`、`OspfInterface.lines`、`OspfNetwork.line`。

**面试会问**："为什么解析结果要带行号？"

**答**：因为后续每一条 Finding 都要能指回证据。如果只剩结构化的值，出了问题只能说"cost 不对"，说不出"第 14 行写的 cost 是 10，基线要求 20"。

**追问**："行号会变，怎么保证不失效？"

**答**：行号只在**同一个配置版本内**有效。版本是不可变的，所以版本 + 行号是稳定坐标。跨版本比较时用 canonical 值，不用行号。

## 5. 未知行不静默丢弃

**代码**：`unparsed: list[SourceLine]`，并且有测试断言未知行被记录。

**面试会问**："解析器遇到不认识的命令，为什么不让它报错退出？"

**答**：两种失败模式要分开：

- **不可用输入**（二进制、NUL 字节、超长）→ 直接报错，`ConfigParseError`
- **可读但不支持的语法** → 记录到 `unparsed`，继续解析

因为真实配置里有大量本项目不关心的命令（`log stdout`、`line vty`）。如果一条不认识就整体失败，解析器就没法用。但如果静默忽略，就会把"没检查"伪装成"没问题"——这是最危险的。

**追问**："那怎么知道哪些真的检查了？"

**答**：`unparsed` 会进入报告，规则引擎对涉及未解析行的判定返回"无法判定"，而不是"通过"。

## 6. 测试策略：真实样本 + 受控变换

**代码**：`samples/frr/r1.conf` 是真实实验配置；`tests/test_drift.py` 每次只改一处再断言。

**面试会问**："你怎么保证漂移检测是对的？"

**答**：

1. 用真实配置做基线，避免自己编的格式和真实世界不一致
2. 每个测试只做**一处**受控变换，期望结果唯一
3. 必测"无变化 → 无漂移"，防止误报
4. 覆盖边界：接口删除、OSPF 进程消失、注释变化、块顺序变化

后续会扩展成 60 个样本的评测集，输出精确率/召回率，而不只是"测试通过"。

## 7. 为什么不用 Batfish？

**面试会问**："Batfish 已经能做配置分析，你为什么重写？"

**答**：两者目标不同。

- Batfish 做**全网转发语义仿真**：给定快照，计算每个包的路径、可达性、ACL 效果
- 本项目做**基线治理**：版本、漂移、规则判定、证据引用、人工审批

我不需要仿真转发，只需要"这条配置偏离基线了吗、违反了哪条规范、证据在哪一行"。用 Batfish 反而要引入 Java 依赖和完整快照模型，而且它的输出不直接对应"规则 ID + 行号"。

**如果被追问"那你的解析正确性怎么保证"**：

坦白说：只覆盖声明过的子集，超出子集的语法进入 `unparsed`，判定返回"无法判定"。**不宣称比 Batfish 更懂配置**，只宣称在自己的范围内可复现。
