## 总体判断

这是一套可以演示「导入 → 设基线 → 比对 → 回查原文」的 W1 原型。SQLite 的唯一约束在实际竞争中守住了两项数据约束。当前最影响可信度的是：文本里已有反证，系统仍可能判符合；有时找到了正确的变更字段，却引用另一条未改的配置行。

**最该补的三件事**

1. 用 [01] 与 [08] 固定规则边界，区分已符合、缺少信息和不适用。
2. 让 [06] 的第二地址改动指向正确原文，把两端值和证据行纳入独立评测。
3. 把 [03]、[04] 的可控交错固定为回归用例，让重复导入返回已有版本，让竞争改基线返回明确冲突。

**面试时最容易被问倒的三个点**

1. 为什么 no ip ospf cost 会让配置实际撤销 cost，规则仍报符合？检查依据是哪一行？
2. 为什么数据库只有一条记录，两个调用方仍会看到不同结果？失败方该如何重试？

### [01] 两个互斥审批可以同时留下成功事件

- 结论：接受
- 位置：domain/netcfg/change_requests.py:transition
- 问题：串行时，draft 或 pending_approval 直接 apply 均因源状态不符返回 409；正常链路必须先 approve，apply 只记录人工标记。风险出在读后写：在临时 SQLite 上，让会话 B 持有 pending 对象，会话 A 批准并提交，B 用仍持有的对象拒绝并提交。实测最终 rejected，事件序列为 created、submit、approve、reject；按状态表，approve 之后不可 reject。未观察到通过正常串行 API 跳过 approve。

- 建议：持久化每次运行的 run_id、version_id 和 counts（包括零 Finding），刷新及默认解释按最新运行读取；每个证据按钮使用该 Finding 自身的 config_version_id。
- 严重级别：高

### [09] 漂移详情的原文按钮缺少可查询的版本 ID

- 结论：接受
- 位置：web/app.js:renderDrift；domain/netcfg/service.py:drift_payload

- 建议：响应补 baseline_version_id；两端按钮分别绑定它与 current_version_id。对同一项断言能分别打开值为 10 和 20 的原文。
- 严重级别：中

### [10] 重复接口块仍可能隐藏撤销命令，令 R001 误判符合

- 结论：接受
- 位置：domain/netcfg/parser.py:parse_frr_config；domain/netcfg/rules.py:run_rules
- 问题：逐行输入下段配置。实测 unparsed 仅记录第 7 行 interface eth0；第 8 行被跳过。返回 4 satisfied、0 undetermined。若导入器不接受重复块，现有信息也不足以证明最终仍显式配置了 cost。

- 建议：保留重复块的子命令，并将受影响的接口规则标记 undetermined；若支持重入，按原顺序合并后运行 R001。

### [11] 地址顺序已保留，重复块内的操作次序仍可能丢失

### [12] 同设备的字节级重复导入由复合唯一约束兜底

## 总体判断

**当前水平**：W2 已能演示从配置、Finding 到变更单、审批及解释的完整流程。串行状态机、数据库去重和解释隔离有可执行的回归证据。当前还不足以把审批历史或刷新后展示的证据作为可靠的审计凭据。

**最该补的三件事**

1. 原子地校验并更新审批状态，让互斥决定只产生一个成功事件，同时让已提交的审计事件只可追加。
2. 统一解释正文与结构化引用的行号集合；让规则检查、刷新及查看原文都绑定具体运行和配置版本。
3. 补工作台端到端验收：首次加载无写入，两端证据按钮各自打开对应版本的原文。

**面试最容易被问倒的三个点**

1. 为什么两个分别合法的审批请求会留下不可能的状态历史？哪一层真正保证状态迁移？
2. 引用中出现正确行号，能否证明正文中的每一条引用都正确？多行证据如何验收？
3. 最新检查零违规时，刷新页面如何证明展示的是本次运行，而不是前一版本的 Finding？
