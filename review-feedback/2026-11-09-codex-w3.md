## B. PostgreSQL 触发器、索引与 JSON

独立 PostgreSQL **17.4** 临时集群，仅监听私有 Unix socket。通过项目 SQLAlchemy 模型、psycopg 3.2.9 和真实的 init_db 执行。测试完成后已关闭；未连接已有业务数据库。

### [B01] 新建、重复启动、缺触发器重启、删表重建均能安装三条触发器

- 结论：确认
- 位置：数据库 engine/models.py 的 AuditEvent / ConfigVersion 表级 after_create、engine/db.py:init_db、engine/bootstrap.py:ensure_append_only。
- 问题与验证：新建表时先创建 prevent_audit_mutation() / prevent_config_version_update()，再注册对应触发器。after_create 不会为已有表重跑。随后每次 init_db 都执行 bootstrap，在同一事务先 CREATE OR REPLACE FUNCTION prevent_mutation()，再 DROP IF EXISTS / CREATE 三条触发器。连续启动两次后，pg_trigger 显示三个触发器都调用 prevent_mutation。提交删除一个触发器并重启后，更新真实记录被拒；对临时库执行 metadata.drop_all 后 init_db，非内部触发器计数恢复为 3。行级操作、父表级联及 TRUNCATE 的实际结果见 C06、C15。
- 建议：用部署角色验收 DDL 权限。本次使用临时实例所有者，生产角色权限未验证。
- 严重级别：低

### [B02] 新库的部分索引有效；已有表缺索引时启动不能恢复它

- 结论：反驳
- 位置：数据库 engine/models.py:Baseline.__table_args__、engine/db.py:init_db、engine/bootstrap.py:ensure_append_only。
- 问题与验证：对「启动后每个库都具备单一 active 保障」的反例：在临时库提交 `DROP INDEX one_active_baseline`，保留 baselines 表，调用 init_db，再查 pg_indexes，匹配数为 **0**。新库实测目录定义为 `CREATE UNIQUE INDEX one_active_baseline ON public.baselines USING btree (device_id) WHERE active`，第二条 active 失败且 inactive 成功（C08）。postgresql_where 的谓词正确。
- 建议：启动检查索引唯一性、键列与谓词。缺失时检查既有重复数据，再建索引或明确拒绝启动。

- 位置：前端 web/app.js:192–198、237、242–245、374。
- 问题与验证：检查正常双版本 API 用例及按钮表达式。第 237 行取 finding.config_version_id || result.config_version_id。完整 Finding 总是优先取自身版本；若提供缺版本字段的行，按钮会绑定运行版本。因此不能承诺「缺字段也一定来自本条 Finding」。数据库写错一个非空版本 ID 时，前端会照用，详见 C09。
- 建议：对缺版本的证据禁用按钮并提示缺失；若已有运行上下文，同时核对两者。
- 严重级别：中

### [UI03] 解释列表可以把不同运行的引用同时呈现

- 结论：反驳
- 位置：前端 web/app.js:189–198、348–349、355–370。
- 问题与验证：对「规则与解释面板始终属于同一 run」：同一设备先后产生两次不同运行的解释，刷新。规则面板按 latest.run_id 请求，解释 GET 路径仅含 deviceId，返回的每一行都展示，无 run 标签。实测向该 GET 返回 B-run1、B-run2，两段文字均出现在解释面板。换设备时旧解释请求也没有写回前的身份核对。
- 建议：明确选中 run_id，规则、解释生成与解释查询共用该值；需要历史视图时明确分组，并显示版本或运行标识。
- 严重级别：中
